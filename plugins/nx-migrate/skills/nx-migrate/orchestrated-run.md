# Orchestrated run

Read from step 5 of `SKILL.md` when the output of `npx nx migrate --run-migrations` holds an `<nx_migrate_runbook run-id="…">` block: Nx started an orchestrated run and drives it. This file applies only then. The reason it defers to Nx for the loop: Nx calls its `RUNBOOK.md` the contract of the run and says it wins over what the session remembers, and a copy here would go stale with the next Nx release.

## The run

- Follow the runbook that Nx printed (and the step blocks it prints) until the run is reported `complete`: the loop through the reconcile command (`nx migrate --run-id=<id>`), a handoff file for each piece of agent work (written with the file-write tool), and commands started in the background with a Monitor in Claude Code, as the runbook says.
- The run's files are in `.nx/migrate-runs/<run-id>`, with `<run-id>` taken from the `<nx_migrate_runbook run-id="…">` block of the current command's output. Read `RUNBOOK.md` and the handoff files only there, and never pick a run directory by glob or by name order. The reason: Nx keeps up to five completed runs in `.nx/migrate-runs` (git-ignored) and reports `existing-run` only for an active one, so a leftover directory of an older run exists without any message. Leftover directories are left alone: not deleted, and not a reason to stop.
- Prompt files that Nx writes to `tools/ai-migrations/` are not workspace content. Nx leaves the directory out of its own commits only while nothing under it is committed yet (it checks the directory as a whole, so one tracked file from an earlier run is enough for Nx to commit the new prompt files as well). While they are left out, step 11 does not stage them and they are listed in the PR body under "Untracked files not committed", as step 11 says for output of a command of this run. When Nx's commits hold them (check `git diff --name-status <start commit>..HEAD`), they are not stopped on and not removed from history; the PR body names them with Nx's commits. This is the orchestrated counterpart of the last sentence of the AI-prompt paragraph in step 5; the clean-up of tracked files there is unchanged.
- Nx makes the commits itself (a checkpoint before the first migration, then one per migration). While the run is active do not run `git commit`, `git reset` or anything that rewrites history, and no unscoped `nx run-many` (the runbook forbids all three in agent work). The skill's own commit (step 11), the `git reset` of its clean-up and the `nx run-many` of step 8 wait until the run is `complete`.
- Prompt work is held to step 5's rules: honour the stated preconditions, a no-op is often correct, do not invent work, and if a prompt names a target the workspace lacks, say so and rely on step 8.
- An `existing-run` report, a refusal at init (`.nx/migrate-runs` tracked or not ignored, the default-branch refusal) and a step that needs the user's direction go to the user. Where nobody is there (the `nx-migrator` agent), stop and report Nx's message, the run id and the step. Do not fall back to the classic loop with `--no-agentic`: that would undo the choice that Nx drives the run.
- If the runbook's Commits section says the run creates no commits (`migrate.createCommits: false` in `nx.json`), nothing is committed before step 11: note the files the steps create and stage them there as in a classic run.

## When the run is `complete`

1. Run `git diff --name-status <start commit>..HEAD`. If Nx's commits hold an entry under `.nx/`, or one that is lint, test or build output rather than migration content, stop and report it. History is not rewritten: Nx's commits stay on the branch, and only a person decides to drop any of them. Step 5 checks that the repository ignores `.nx/cache` and `.nx/workspace-data` before the run, so this only happens when something else wrote such a file.
2. Record for the PR body (step 12) the outcome of each step as the run reported it (applied, adopted, skipped, unresolved) and the commits (`git log --format='%h %s' <start commit>..HEAD`). A step 4 lockfile regeneration is recorded for the PR body's "Lockfile regenerated" line and is not named in the step 11 commit, because Nx's checkpoint commit holds it. This holds only for a run that creates commits; in a run without commits (the `migrate.createCommits: false` bullet above) the step 11 commit holds the regenerated lockfile and names it, as in a classic run.
3. Continue with step 6. When the run created commits, the files the steps created are already in them and are not noted for step 11. Step 8 still runs in full (its first runs skip the cache, step 8): Nx's final validation pass is limited to `nx affected` with a base ref and does not replace it.
