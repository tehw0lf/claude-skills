# Orchestrate issues

Drives the sequence a person otherwise runs by hand: for each issue the context check, `work-issue:issue-planner`, then `work-issue:issue-worker`, which implements, gets the independent review and merges as its own file says. This skill decides nothing about an issue: the planner plans, the worker works, their reports are relayed, not re-judged.

**Run it in the main session, never inside a subagent.** The worker needs its spawn depth for `pr-review:pr-reviewer`; an orchestrator that is itself a subagent takes a level of it, and at the limit the `Agent` tool is withheld.

Nothing is scheduled: an issue that waits for an owner answer ends this run at its questions, and calling the skill again picks it up (`QUESTIONS … answered`); an answer given only in the chat of a session counts once it is on the issue (step 4); start that call in a new session where you can, because a second call in the same session shares its context with the first. An issue that is already started is continued where it stands, until its PR is merged: the current plan is used as it is, and an own open PR goes back to the worker (step 3). To start it from a timer or a routine, read `scheduling.md` first; it also describes a dispatcher that starts one session per repository with work, several in parallel (`--parallel`), each with this skill scoped to its repository.

## Steps

### 1. Select

```bash
<skill directory>/scripts/run-context.py [--label <name>] [--owner <login>]... [--checkout owner/repo=<path>]... [owner/repo | 'owner/repo#n']...
```

Call it by its full path (`--help` describes the output). Arguments: `owner/repo#n` is an explicit issue (naming it is the consent); `owner/repo` takes every open issue of that repository that carries the label (`auto-work`); `--owner <login>` (an account or an organisation; only this flag makes a name an account, a bare word is an error; repeatable) takes the same from every repository of it that has an open issue with the label, found by one issue search (archived repositories are left out; the `SCOPE` line gives the number of repositories found, and the search index can lag behind a label set just before the call, so such an issue is found by the next run); no argument means the repository of the current directory in label mode, never an account. The repository gate is unchanged and applies per repository: the `CHECKS` line of each (step 5). Report every `# SKIPPED` line. A non-zero exit: report its reason and stop.

A labelled issue is taken only when its `ISSUE` line shows a labeler with permission `admin`, `maintain` or `write`. Reason: triage users can add labels without having merge rights, and an issue form can apply labels automatically (the labeler is then whoever opened the issue); without the check anyone who can open an issue could start an unattended merge. A labeler or permission shown as `-` (unreadable, or the label was removed again: the `# SKIPPED labeler` line says which) is not taken. A custom repository role is judged by the base permission it is built on and shown as that (`write` counts, `read` does not), so an organisation's own roles are not shut out. The same holds for the `edit` field: an issue whose body or title was ever edited, before or after the label event, by any account without `admin`, `maintain` or `write`, or by a deleted account (`untrusted`), or whose edit history could not be read in full (`-`), is not taken. The script reads the whole history, not only the newest editor, so an untrusted edit followed by a writer's edit is still `untrusted`. Reason: the author of an issue can edit it at any time. An edit after the label changes what the owner agreed to, and an edit before it may be newer than what the owner read (a labeller who opened the issue earlier, or labels from a list, agrees to a revision that is no longer the current one). Edits by an account with write access are the owner's own changes and do not stop the issue. Explicit references are exempt (naming the issue is the consent). An issue that is both named and labelled appears once, as `ref`. Name every issue dropped this way in the report.

The label is not created by this skill; a missing label finds nothing, and the report says so. `work-issue:propose-auto-work` is the skill that proposes the label per issue, sets it on the user's confirmation and creates it on request. The script reads the label-filtered listing and the unfiltered open-issue listing, because the filtered one can lag behind a label that was only just set; an issue found by either is listed once.

### 2. Checkouts

Per repository, once per run, the first of:

1. a `CHECKOUT … given` line;
2. the first `CHECKOUT … found` line that is `clean` and on the default branch of the `REPO` line;
3. `gh repo clone <owner/repo> <scratch directory>/<owner>-<repo>` (a fresh clone is on the default branch).

A found checkout that is dirty or on another branch is not used. Reason: the worker stops on a dirty working tree, and a checkout on another branch is probably in use by another session that the worker's `git switch` would disrupt; a clone is never the owner's working copy. Such a checkout is named in the report (step 7) with its path, state and branch, and nothing in it is discarded, reset or switched. A given checkout (item 1) is used as given, even when dirty or not on the default branch, since the caller chose it (the worker stops there if the tree is dirty); it is only named in the report, with the same details; when its branch has a path segment that starts with the number of an issue of this run for that repository (the pattern of `print_branches` in `issue-context.py`), the report adds "possibly left by an aborted run of #<n>". An aborted worker run can leave exactly that: the run's branch with uncommitted work or unpushed commits. A failed clone ends that repository's issues with a report.

### 3. Context per issue

Run `<skill directory>/../work-issue/scripts/issue-context.py 'owner/repo#n'` inside the issue's checkout and apply the stop conditions of step 1 of `work-issue` (closed, a `PR` that is `open` and `closes` and is not an own PR as below, an assignee other than `ACCOUNT`, `CHECKOUT` not `match`, a skipped source a condition depends on, `# SKIPPED plan`). An issue that stops there is reported with the reason. `QUESTIONS … open` is reported with the comment link: the issue waits for the owner, unless the owner answered those questions in the chat of this session, then step 4 applies first.

**An own open PR is continued, not a stop.** An open `PR … closes` is an own PR when the output has a `RESUME` line for it whose plan field equals the id of the `PLAN … current` line or the id in the last field of that line (the plan it adopts, see `plan-issue`'s `adopt.md`). **An unanswered stop marker on the PR head comes first, whatever the plan field** (first bullet below): the PR is reported as "waiting for a person" and nothing else is decided. Otherwise a `RESUME` line whose plan field is `-` is reported as "own PR that does not link the current plan", with the PR link, for a person to decide; an open PR without a `RESUME` line stays "somebody is on it". A `RESUME` line whose plan field is another id (a replan after an owner comment made the plan stale, or a plan the current one does not adopt) is not a stop for the planner: with a `PLAN … stale` line or no `PLAN` line the issue is taken and goes to step 4, where the planner judges the PR (adopt it or ask the owner, `adopt.md`); with a `PLAN … current` line the plan stands and a planner would change nothing, so it is reported as "own PR on a plan other than the current one", with the PR link, and nothing is spawned. An own PR on the current or the adopted plan is continued. Then:

- the newest stop marker of the `RESUME` line names the PR's current head (the head field; compare by prefix) **and** the line does not say `answered`: report "waiting for a person on PR #m", with the reason, and spawn nothing. It costs nothing against the limit. The `issue-worker` wrote the marker because a person has to act (a finding, a red check, a merge by hand); a push or an owner comment on the PR releases it. The reason `pending-check` is the exception, because no person has to act: read the checks with `gh pr checks <PR> -R <owner/repo> --required --json name,bucket` (the listing the worker stops on; exit 1 with "no required checks reported" lists none) and compare them with the names of the repository's `CHECKS` line. When every named check is there with the bucket `pass`, the issue is taken like an own PR without a marker (below). Otherwise spawn nothing, at no cost against the limit: a named check that is missing or pending is reported as "waiting for required checks on PR #m", a red one (`fail`, `cancel`) or a skipped one (`skipping`, concluded but not green) as "waiting for a person on PR #m" with the check's state, which a re-run of the check or a push releases. A `CHECKS` line with `- -` releases nothing here (the marker waits for a person)
- `RESUME` says `unknown`: report it; nothing is spawned (the next run tries again)
- `RESUME` says `conflicting`: taken like an own PR without a marker (the next bullet). The worker resolves a version-only conflict under "Merging" and stops with the marker reason `conflict` on any other; the first bullet then reports that as "waiting for a person on PR #m" until a push or an owner comment releases it. Reason: the selection reads only GitHub's state and cannot tell a version-only conflict from another, and the marker limits the cost to one worker run per head
- otherwise the issue is taken, skips step 4 (there is a plan and a PR) and goes to step 5 with the PR named

**An own pushed branch is finished, not a stop.** A `PUSHED` line whose plan field equals the id of the `PLAN … current` line or the id in its last field (the plan it adopts) is the branch of an earlier worker run that was aborted between `git push` and `gh pr create` (its commits carry the trailer of step 8 of `work-issue`). **Parked:** when the output also has a `FINISHSTOP` line for that branch with the same head (compare by prefix with the `PUSHED` head), the plan id of the `PLAN … current` line itself (the finish marker names the current plan id even when the branch is on the adopted one), an attempt of 2 or more and no `answered`, the worker stopped twice on this head and nobody has acted since: report "branch <name> parked: <reason>; to release it, a person with write access posts a comment whose first line is `<!-- work-issue:finish-released branch=<name> head=<PUSHED head, full> plan=<PLAN id> -->`" (values filled in; the reason is the reason field of the line) and spawn nothing; it costs nothing against the limit. The orchestrator does not post the release marker. A `FINISHSTOP` with attempt 1 is the one automatic retry and does not park: the branch is taken as below (the retry is this run's worker; a second worker in the same run is not started, see step 6). A new head or plan releases it. So does a release marker as above: it sets `answered` and keeps the `PLAN` current, so the branch is taken again on the same plan. A plain comment of a writer on the issue does not release: it makes the `PLAN` stale (`owner-comment`), so the issue goes to the planner (the rule below), which adopts the branch or asks the owner; the worker never retries it by itself. Otherwise the issue is taken when no other stop condition applies, skips step 4 (there is a plan) and goes to step 5 with "finish branch <name>". A `PUSHED` line whose plan field is not `-`, not the id of the `PLAN … current` line and not the id that line adopts (another plan, the same id on a `PLAN … stale` line, or no `PLAN` line) is not a stop for the planner either: with a `PLAN … stale` line or no `PLAN` line the issue is taken and goes to step 4, where the planner judges the branch (adopt it or ask the owner, `adopt.md`; a replan that did not adopt it would orphan it, and `work-issue` step 1 stops on such a branch); with a `PLAN … current` line the plan stands and it is reported as "own branch <name> on a plan other than the current one", and nothing is spawned. When it is reported, for the same id the report adds the stale reason from the `PLAN` line. A `PUSHED` line with `-` is somebody's branch and stays as `work-issue` step 1 treats it.

Take the remaining issues in order, explicit references in the given order first, then labelled ones oldest first across all repositories, until the limit of **1 issue per run** (`--max <n>` overrides it; issues named explicitly count against the limit too, so naming two issues needs `--max 2`). Only an issue for which a planner or worker is spawned counts; the ones that ended above cost nothing. Issues beyond the limit are listed as not taken. Reason for 1: the issues of one run share the context of one session, so details of an earlier issue stay present while the next is worked and the context grows with each issue; one issue per run, each run in a new session (as the scheduled runs in `scheduling.md` start), keeps the context small, lets nothing of one issue leak into the next, whereas a second call in the same session shares the context like a higher `--max`; and keeps the usage per run low (each issue can still cost two Opus planner runs, two Sonnet worker runs and an Opus first review round, and the model split exists because of the usage limit). The default also bounds the unattended merges before a person looks: a higher `--max` is the caller's explicit decision to accept more unattended merges and more shared context. `--max` counts issues taken, not the follow-up issues their review rounds open: every round can add some, they carry no `auto-work` and so a later run in label mode does not take them (one named explicitly is taken), and they accumulate as work for a person, which a caller raising `--max` should account for.

### 4. Plan

**An answer given in the chat goes on the issue first.** When the owner answered an issue's open questions in the chat of this session, do not spawn the planner yet and do not put the answer into its prompt. Show the owner the comment exactly as it will be posted: the answer verbatim, then a blank line and the origin line `*[orchestrate-issue] owner's answer, copied verbatim from the session*`. The first line must not be a `<!-- work-issue:… -->` marker. Post it only on the owner's confirmation in the chat; the owner may correct the text, and as a public comment it carries nothing from outside the repository. To post it, run `mktemp -d` as its own command, write `comment.md` with `Write` into the printed directory (the path used literally), and run `gh issue comment <n> -R <owner/repo> --body-file <path>/comment.md`. Then run `issue-context.py` again and spawn the planner only on `QUESTIONS … answered`. Reason: the planner and `issue-context.py` count only issue comments as answers (`plan-issue` reports `QUESTIONS … open` and stops; `issue-context.py` sets `answered` only for a later unmarked comment by `ACCOUNT` or a writer; step 3 above ends the issue at `open`), so a chat answer leaves the questions open whatever the session does. In earlier runs the auto-mode classifier also denied the planner's write after a chat answer (not reproduced, the denial text was not kept). An approval to start the planner alone does not help, for the same reason.

For each taken issue without `PLAN … current` (an issue with an own PR to continue has one), spawn `work-issue:issue-planner` with the issue reference and the checkout path. Planners of different issues may run in parallel. Then run `issue-context.py` again. When the planner wrote a plan that adopts an own PR or pushed branch (the `PLAN … current` line now ends in the adopted id), apply the own-PR and own-branch rules of step 3 again before step 5, so that the worker gets "resume PR #m" or "finish branch <name>"; without this step 5 would start the worker without either. An `ISSUE … closed` line together with a planner report of a close (with the link of its `closed` comment) is the outcome "closed on the owner's answer", reported with that link, and nothing further is spawned for it; a closed issue without such a report was closed by someone else during the run (a person, a merged PR) and is reported as closed during the run. `QUESTIONS … open` is reported with the link; `PLAN … current` goes to step 5; anything else is reported.

### 5. Work

Read the required status checks from the `CHECKS` line of the issue's repository (names are tab-separated) and spawn `work-issue:issue-worker` with the issue reference, the checkout path, for an own PR "resume PR #m", for an own pushed branch "finish branch <name>" and, in its prompt:

- **at least one required check:** the names, and that in addition to its own merge rules each named check must appear as `pass` in `gh pr checks <PR> --required` on the reviewed head; a named check that does not appear is not green, and a named check that does not appear or has not concluded when its bounded wait ends is a stop with the marker reason `pending-check`, which the next run resumes (step 3). Reason: the worker's own rule covers only checks that report, and a merge by an account that may bypass a ruleset would not be held by GitHub.
- **no required check, or any `# SKIPPED rules` / `# SKIPPED protection` line for the repository** (the script then prints `- -`, since a list from one source may be incomplete): that it must not merge. It runs its review rounds, opens follow-up issues as its file says and stops where it would merge. Reason: a check that reports on a PR but is not required (an installed app) can be green without verifying the change, and a green status alone is not a required check. The report then names the open PR, its reviewed head and the verdict for a person to merge, and the skipped source when there was one.

One worker per repository at a time; repositories may run in parallel. Reason: workers of one repository touch the same manifests and collide on rebase and version numbers.

### 6. Rounds

A round is one plan (existing or new) and one worker run; an issue gets at most **2 worker runs**, so one replan. Only the worker's three plan stops go back to the planner, with the stop named in its prompt: the files under **Changes** moved, the code did not show the plan's cause, the issue waits for an open `REF`. Then steps 4 and 5 once more. A worker that finishes an own branch is not replanned either, like one that resumes a PR: it has no plan stops, and a replan would orphan the branch. Its stop is not retried in the same run: the finish marker it wrote, if the stop writes one (`worker-stop-marker.md`, "Finish marker"), makes the next run's step 3 see attempt 1 and take the branch once more, and after the second stop the branch is parked; a stop without a marker leaves the branch to be taken again by the next run. A worker that resumes a PR is not replanned: it has no plan stops, and a replan on top of an open PR would orphan it. Any other stop (validation, `blocking`, non-converging `fix-in-PR`, a red or missing check, a refused merge, no reviewer, no current plan, an outside open pull request that changes files of the plan) ends the issue with the worker's report. The last one is released only by the owner's answer, which the planner records under **Decisions**: a later run of the same issue stops there again until then, so the report names the pull request.

### 7. Report

Per issue: the outcome (merged PR; open PR awaiting a person, with the reason; closed on the owner's answer, with the link of the close comment; parked branch, with the finish marker's reason and the release line; questions with the comment link; waiting for a person on a PR, with the marker's reason; stopped, with the reason; not taken because of the limit or the labeler) and what was not verified. Relay the agents' reports; do not re-judge them. The checkouts named in step 2 (dirty, or on another branch) are part of the report. Done when every selected issue has one outcome line.
