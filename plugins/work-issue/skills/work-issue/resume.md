**Resume an own PR.** A PR that an earlier run of this skill opened and that is still open is continued, not left to whoever happens to look at it. It is the account's own work only when a `RESUME` line for that PR exists (open, closes the issue, written by `ACCOUNT`, head branch in this repository) **and** its plan field equals the comment id of a `PLAN … current` line (step 8 puts the plan link into the PR body). Reason: `ACCOUNT` is usually the owner's own login, so the author alone would take a PR the owner opened by hand and merge it unattended; and a PR built on an older plan is not what the current plan says. A PR that is not recognised this way stops the work as above; when a `RESUME` line exists but its plan field is `-` (the body links no plan comment) the report says "own PR that does not link the current plan", and when the field names another plan than the current one (the issue text was edited or the owner commented on the issue after the plan, so `PLAN` is `stale`) it says "own PR on a plan that is no longer current"; a person decides either way, with no replan on top of the open PR.

For an own PR, steps 2, 3, 5, 6 and 8 do not apply: nothing is planned, changed, bumped, committed or pushed, and the plan's base commit is not compared (the PR exists, and `RESUME` reports `mergeable`). What runs:

- `RESUME` says `conflicting`: stop and report; resolving a conflict is a change. `unknown` means GitHub has not computed mergeability yet: run `issue-context.py` again once after a minute; when it is still `unknown`, end the run with a report that says so. The `issue-worker` writes no stop marker for it, because nothing is wrong with the PR.
- Put the PR's branch under the checkout. First `git fetch origin`, then, as its own command, `git rev-parse --verify refs/remotes/origin/<branch>`: its output must equal the head that `RESUME` names. A different head (somebody pushed after `issue-context.py` read the PR) or a failing command is a stop before the switch: report both heads, or the command's message, and touch nothing. This stop writes no stop marker, as for `unknown`, because nothing is known to be wrong with the PR and the next run reads the new head through `RESUME`; a marker written for the new head would park a healthy PR. The comparison comes right after the fetch because nothing reads the remote again after it (the switch and `git merge --ff-only` use the local remote-tracking ref), so it closes the window completely. Then `git switch --no-overwrite-ignore --track refs/remotes/origin/<branch>` when there is no local branch of that name, otherwise first `git rev-list --count refs/remotes/origin/<branch>..refs/heads/<branch> --` (the commits the local branch has and the remote does not), and only when it prints exactly `0` `git switch --no-overwrite-ignore <branch>` and `git merge --ff-only --no-overwrite-ignore refs/remotes/origin/<branch>` (`git switch` takes branch names only, so `<branch>` stays as it is there). Every ref is written out in full because a short name resolves a tag of the same name before the branch (the count would be `0` although the local branch is ahead) and a local branch named `origin/<branch>` before the remote-tracking ref (the fast-forward would merge the wrong commit). A `rev-list` that fails (a non-zero exit, for example because the branch does not exist) or prints something other than a single number is a stop before the switch as well: report the command's message, touch nothing, and write no stop marker, for the same reason: the check could not be evaluated, which says nothing about the PR. Any other count means the local branch is ahead of or has diverged from the remote and holds commits nobody pushed: stop before the switch and report the branch and the count, touch nothing: nothing is deleted, reset or pushed, and the commits stay for a person. Running unsupervised, the `issue-worker` ends this stop with a stop marker (reason `other`, one sentence naming the branch and the count), written for the PR's current head read with `gh pr view <PR> -R <owner>/<repo> --json headRefOid -q .headRefOid`, because without one every later orchestrator run takes the issue again and stops at the same place. The check comes before the switch because `git merge --ff-only` exits 0 with "Already up to date." on a branch that is only ahead, so nothing after the switch would stop the run and step 7 would validate a commit that is not the PR head. Reason for the option: git replaces an ignored file by default when the PR branch tracks something at its path (a file at the path of an ignored file or directory, or a directory where an ignored file sits), and the switch back at a stop then deletes it; step 1's clean check does not see ignored files. When git refuses, it names the paths (untracked files that would be overwritten, or directories that would lose untracked files): stop and report those paths, a person decides whether the local file may move. The ignored file is neither moved nor deleted (a refused `git merge --ff-only` after the switch still gets the clean-up of "Stopping after the branch exists" (`stopping.md`), which leaves ignored files alone). Running unsupervised, the `issue-worker` ends this stop with a stop marker (reason `other`, one sentence saying that an ignored file in the local checkout would be overwritten by the PR branch, with the number of refused paths and no path), written for the PR's current head read with `gh pr view <PR> -R <owner>/<repo> --json headRefOid -q .headRefOid`, because without one every later orchestrator run takes the issue again and stops at the same place while the file is there. The marker sits on the PR while the cause is a file in one checkout, so a run from another checkout also skips the PR until a push or an owner comment on the PR releases it; if the file is still there then, the next run stops again with a new marker. That cost is accepted: the alternative is a scheduled run that spends its slot on this issue every time.
- Record the untracked entries right after the successful switch (and after `git merge --ff-only`), as its own command: `git -c core.quotePath=false status --porcelain --untracked-files=all > <temporary directory>/status-after-switch.txt` (the temporary directory is the one created as step 1 says). Step 7 compares against it. It comes after the switch because the entries of the PR branch's ignore rules are the ones step 7 sees: a file whose ignore rule the PR removed (a project `.npmrc`) is `??` from here on and must not be taken for validation output. A failed write is a stop on the PR branch and gets the clean-up of "Stopping after the branch exists" (`stopping.md`).
- Step 4 installs the dependencies (no reproduction), step 7 validates the head that `RESUME` names. A failing validation is not fixed here: stop and report it. This skill commits and pushes nothing on a resumed PR. A fix for a `fix-in-PR` finding of a review is made by the `issue-worker` after the review, as its file says under "Resuming an own PR"; a person decides only what that file leaves to one.
- Done when step 7 holds for the PR head. Report the PR, the head, the validation result and the verdict head from `RESUME`.

A stop on unpushed commits, on a fetched head that differs from the one `RESUME` named or cannot be read, and on an unpushed-commits check that cannot be evaluated (above) leaves the checkout unchanged as well, and none of the commands below run. A refused `git switch` (above) leaves the checkout on the branch step 1 found with nothing changed, and no local branch is created by a refused `--track`: none of the commands below run. A refused `git merge --ff-only` after a successful switch is a stop on the PR branch and gets the clean-up of "Stopping after the branch exists" (`stopping.md`). Otherwise a stop in resume mode puts the checkout back in three separate commands (step 1 found the working tree clean, so every uncommitted change, and every file that is untracked under the ignore rules of the branch step 1 found, is this run's own; ignored files that were there before are protected by `--no-overwrite-ignore`, not by step 1's clean check):

1. `git reset --hard` on the PR branch: it discards what the install and the validation changed in tracked files (a rewritten lockfile).
2. `git switch <branch WORKTREE named>` (or `git switch --detach <commit kept in step 1>`): untracked files come along.
3. `git clean -fd`, only after the switch succeeded; ignored files stay, no branch is deleted.

The three are run as written, without a trailing comment (the example permission list of `orchestrate-issue` allows `git reset --hard` and `git clean -fd` as exact commands).

Run the clean only when the switch exited 0: after a failed switch the checkout is still on the PR branch, whose ignore rules would make it delete files that are not the run's own. If the switch fails (an untracked file the run wrote sits at a path the previous branch tracks), run no `git clean`: leave the checkout on the PR branch and report the paths git names. Reason: a lockfile that the install rewrote differs between the PR branch and the default branch, so a switch without the reset either refuses or carries the change onto the default branch, and the next run stops on a dirty checkout. The clean runs on the previous branch because its ignore rules are the ones step 1's clean check was made under; on the PR branch a file whose ignore rule the PR removed (a project `.npmrc`) counts as untracked and would be deleted. The commits stay on the remote.
