**Finish an own branch.** The branch is the one whose `PUSHED` line carries the id of the `PLAN … current` line or the id in its last field, the plan it adopts (`PUSHED <branch> <head sha> <count> <plan id>`). Its commits were made by an earlier run of this skill on the current plan or the plan it adopts (each carries the `Work-issue-plan` trailer of step 8, all with this plan's id), and the run was aborted before `gh pr create`. Reason it is recognised by the trailer and not by the branch name or the account: `ACCOUNT` is usually the owner's own login, and a branch the owner made by hand must not be finished and merged unattended. One commit without the trailer (a hand-made commit on top) makes `issue-context.py` print `-` as the plan id, and the branch is somebody's started work.

Steps 2, 3, 5 and 6 do not apply: nothing is planned, changed, bumped or committed, and the plan's base commit is not compared. The branch was built on the current plan or the plan it adopts (the new PR links the current plan, as step 8 says); a default branch that moved since is handled after the PR exists, by the branch update under "Merging" of the `issue-worker`. What runs:

- Put the branch under the checkout exactly as the second bullet of `resume.md` describes for a PR branch (fetch; `git rev-parse --verify refs/remotes/origin/<branch>` must equal the head of the `PUSHED` line; `git switch --no-overwrite-ignore --track` for a missing local branch, otherwise the `rev-list --count` check and the `--ff-only` fast-forward), with the `PUSHED` head in the place of the `RESUME` head. The difference: none of these stops writes a stop marker, because no PR exists to carry one. Run by the `issue-worker`, the failed fetch or `rev-parse`, the differing head and the unevaluable `rev-list` write no finish marker either (`worker-stop-marker.md`, "Finish marker"); the local-ahead stop and the refused switch or fast-forward do get one.
- Record the untracked entries right after the successful switch (and after `git merge --ff-only`), as in the third bullet of `resume.md`: `git -c core.quotePath=false status --porcelain --untracked-files=all > <temporary directory>/status-after-switch.txt`.
- Step 4 installs the dependencies (no reproduction). Check that the branch holds the version bump step 6 would make: `git diff --name-only refs/remotes/origin/<default>...HEAD` has to list the file or files that step 6 bumps: those the repository's versioning rule names, otherwise the manifest (and lockfile) of the root `MANIFEST` line. Without it stop and report "own branch without the version bump".
- Step 7 validates the head. A failing validation is not fixed here: stop and report it.
- Green: step 8 without commit and push. Open the PR with `gh pr create --base <default> --head <branch> --title "<type>(<scope>): <what changes>" --body-file <temporary directory>/pr-body.md`, the body as step 8 describes it (`Closes #<n>`, the plan link, **Why**, **What**, **Verification**, **Not verified**). **What** is written from the branch's diff against the default branch (`git diff refs/remotes/origin/<default>...HEAD`) and names the bump commit as the diff shows it; it says that the version scripts' run during the bump was not observed by this run. **Not verified** says that this run did not make the commits.
- Done when the PR is open on the head of the `PUSHED` line for which step 7 held. Report the `PUSHED` line, the PR and the validation result.

A branch that is or was the head of a pull request never gets a `PUSHED` line (`issue-context.py` looks at pull requests of every state), so a closed or merged PR is not put up again by this mode.

The skill itself writes nothing to GitHub in finish mode: there is no PR for a stop marker. Run by the `issue-worker` agent, a stop here, except the stops that the first bullet says write no finish marker (failed fetch or `rev-parse`, differing head, unevaluable `rev-list`), ends with the finish marker, one comment on the issue (`worker-stop-marker.md`, section "Finish marker"): the next run retries the branch once and, if it stops on the same head and plan again, the branch is parked and the orchestrator leaves it to a person, who releases it with the release marker (`worker-stop-marker.md`, section "Finish marker"). Without the agent nothing is written, and the next run finds the same branch and stops again until a person acts. Say in the report which of the two applies, or, for one of those stops, that the next run tries the branch again. The clean-up is that of resume mode in `resume.md` (the three commands and their conditions: a stop before the switch leaves the checkout unchanged and runs none of them; a refused `git merge --ff-only` after the switch, or a stop after it, gets `git reset --hard`, `git switch` to the branch `WORKTREE` named or `git switch --detach` to the commit kept in step 1, and `git clean -fd` only after the switch succeeded). The commits stay on the remote.
