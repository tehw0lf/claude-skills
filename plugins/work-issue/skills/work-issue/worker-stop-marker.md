## Stop marker

Every stop **after the PR exists** (a stop before it leaves nothing on GitHub, see "Stop instead of asking") ends with one comment on the PR, written last, before your report:

```bash
gh pr comment <PR> -R <owner>/<repo> --body-file <file>
```

The file starts with the line `<!-- work-issue:stopped head=<full sha of the PR head> reason=<kind> -->`, then a blank line, the origin line `*[work-issue] stop marker, written by the issue-worker agent*`, a blank line, and one sentence in terms of the code or the diff (the rule on PR texts: nothing from logs, runs, paths or sessions). `<kind>` is one of `blocking`, `no-convergence`, `red-check`, `not-runnable`, `merge-refused`, `no-reviewer`, `conflict` (only a PR that is really `conflicting`; an `unknown` mergeable state is no stop and gets no marker; nor does a resume stop before the switch where the fetched PR head differs from the head `RESUME` named or cannot be read, or where the check for unpushed commits cannot be evaluated; nor do the stops of the branch update under "Merging" where `mergeStateStatus` stays `UNKNOWN`, the update has not landed within the minute, the fast-forward is refused for another reason than an ignored file, or the branch is `BEHIND` again after the update round or right before the merge, or the merge is refused because the head is not up to date: nothing is known to be wrong with the PR, and the next run reads it again), `awaiting-merge` (the run was told not to merge, or the review is clean and a person has to merge), `pending-check` (the review is clean, but a required check named in the prompt had not reported or not concluded on the head when the bounded wait under "Merging" ended; no person has to act: the next orchestrator run, and `has-work.py` before it, read the checks again and resume the PR once every required check passes), `other` (also the resume stop before the switch because the local PR branch holds commits that are not on the remote: one sentence naming the branch and the number of local commits, written for the head the PR has now, read with `gh pr view <PR> -R <owner>/<repo> --json headRefOid -q .headRefOid`; nothing is deleted or reset, the commits stay for a person; also the resume stop where git refuses to switch to the PR branch or to fast-forward it because an ignored local file would be overwritten: one sentence saying that an ignored file in the local checkout would be overwritten by the PR branch, with the number of refused paths and no path, written for the head read with the same `gh pr view` command; the ignored file is neither moved nor deleted (a refused fast-forward still gets the skill's clean-up, which leaves ignored files alone), the report names the paths, and the marker also makes a run from another checkout skip the PR until a push or an owner comment releases it). Reason: without it the next orchestrator run cannot tell a PR that waits on a person from one a crashed run left behind, and would validate and review it again every time. The marker names the head it was written for: a push makes it obsolete, and so does an owner comment on the PR (`issue-context.py` reports it as `answered`). The origin line is never line 1: `issue-context.py` reads only the first line of the comment as the marker. A run that merges writes none. After the marker the checkout goes back as under "Back to the starting branch"; the marker stays the last write to GitHub.
