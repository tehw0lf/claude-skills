## Stop marker

Every stop **after the PR exists** (a stop before it leaves nothing on GitHub, see "Stop instead of asking", except a stop in finish mode, which ends with the finish marker on the issue, see "Finish marker" below) ends with one comment on the PR, written last, before your report:

```bash
gh pr comment <PR> -R <owner>/<repo> --body-file <file>
```

The file starts with the line `<!-- work-issue:stopped head=<full sha of the PR head> reason=<kind> -->`, then a blank line, the origin line `*[work-issue] stop marker, written by the issue-worker agent*`, a blank line, and one sentence in terms of the code or the diff (the rule on PR texts: nothing from logs, runs, paths or sessions). `<kind>` is one of `blocking`, `no-convergence`, `red-check`, `not-runnable`, `merge-refused`, `no-reviewer`, `conflict` (only a PR that is really `conflicting`; an `unknown` mergeable state is no stop and gets no marker; nor does a resume stop before the switch where the fetched PR head differs from the head `RESUME` named or cannot be read, or where the check for unpushed commits cannot be evaluated; nor do the stops of the branch update under "Merging" where `mergeStateStatus` stays `UNKNOWN`, the update has not landed within the minute, the fast-forward is refused for another reason than an ignored file, or the branch is `BEHIND` again after the update round or right before the merge, or the merge is refused because the head is not up to date: nothing is known to be wrong with the PR, and the next run reads it again), `awaiting-merge` (the run was told not to merge, or the review is clean and a person has to merge), `pending-check` (the review is clean, but a required check named in the prompt had not reported or not concluded on the head when the bounded wait under "Merging" ended; no person has to act: the next orchestrator run, and `has-work.py` before it, read the checks again and resume the PR once every required check passes), `other` (also the resume stop before the switch because the local PR branch holds commits that are not on the remote: one sentence naming the branch and the number of local commits, written for the head the PR has now, read with `gh pr view <PR> -R <owner>/<repo> --json headRefOid -q .headRefOid`; nothing is deleted or reset, the commits stay for a person; also the resume stop where git refuses to switch to the PR branch or to fast-forward it because an ignored local file would be overwritten: one sentence saying that an ignored file in the local checkout would be overwritten by the PR branch, with the number of refused paths and no path, written for the head read with the same `gh pr view` command; the ignored file is neither moved nor deleted (a refused fast-forward still gets the skill's clean-up, which leaves ignored files alone), the report names the paths, and the marker also makes a run from another checkout skip the PR until a push or an owner comment releases it). Reason: without it the next orchestrator run cannot tell a PR that waits on a person from one a crashed run left behind, and would validate and review it again every time. The marker names the head it was written for: a push makes it obsolete, and so does an owner comment on the PR (`issue-context.py` reports it as `answered`). The origin line is never line 1: `issue-context.py` reads only the first line of the comment as the marker. A run that merges writes none. After the marker the checkout goes back as under "Back to the starting branch"; the marker stays the last write to GitHub.

## Finish marker

Every stop in finish mode (`finish-branch.md`) **before `gh pr create` succeeded** ends with one comment on the issue, written last, before your report. This includes the stop where `gh pr create` itself fails; it excludes every stop after the PR exists (that one gets the stop marker above). It is the one write to an issue that this agent makes. The marker lets the next orchestrator run see that the branch was tried on this head and, after the second stop, leave it to a person instead of installing and validating it again on every tick.

```bash
gh issue comment <issue number> -R <owner>/<repo> --body-file <file>
```

The file starts with the line `<!-- work-issue:finish-stopped branch=<branch> head=<full sha of the PUSHED head> plan=<plan comment id> attempt=<attempt> reason=<kind> -->`, then a blank line, the origin line `*[work-issue] finish marker, written by the issue-worker agent*`, a blank line, and one sentence in terms of the code or the diff (nothing from logs, runs, paths or sessions). The origin line is never line 1: `issue-context.py` reads only the first line of the comment as the marker. `<kind>` is one of `install` (the install of step 4 failed), `no-bump` (the branch holds no version bump), `validation` (step 7 failed or could not run), `head-mismatch` (`origin/<branch>` is not the `PUSHED` head), `local-ahead` (the local branch holds commits that are not on the remote), `switch-refused` (git refuses to switch or fast-forward because an ignored local file would be overwritten), `pr-create` (`gh pr create` failed), `other`.

The marker names the id of the `PLAN … current` line in `plan=`, also when the branch is on the plan that line adopts (`PUSHED` carries the adopted id), so adoption starts at attempt 1. `<attempt>` is the attempt count: take the `FINISHSTOP` line for your branch from the output of step 1. When its head equals the `PUSHED` head (by prefix), its plan equals the id of the `PLAN … current` line and it is not `answered`, write its attempt plus 1; otherwise write 1. The marker is valid only while the `PUSHED` head and the `PLAN` id stay the same: a new head or plan starts at 1. A person with write access releases a parked branch by hand: a comment on the issue (`gh issue comment <n> -R <owner>/<repo> --body-file <file>`, or the web UI) whose first line is `<!-- work-issue:finish-released branch=<branch> head=<full sha of the PUSHED head> plan=<plan comment id> -->`, then a blank line and one sentence on what was done about the reason (no script reads it). It counts (`FINISHSTOP … answered`) only after the finish marker, for the same branch, the same plan and a head that equals the marker's (by prefix); `issue-context.py` treats it as a marker like the plan and questions comments, so the `PLAN` stays current and the next run retries the branch. A release resets the attempt count: the next finish marker is attempt 1 (the rule above). A release comment carries no new requirements; a change of what is wanted is an ordinary comment. A plain comment of a writer does not release: it comes after the plan and makes the `PLAN` stale (`owner-comment`), and the next orchestrated run sends the planner, which does not adopt a branch with an unanswered finish marker of attempt 2 or more without asking the owner (`adopt.md`); the worker never retries it by itself, and `work-issue` step 1 stops on a branch whose plan is neither the current one nor the one it adopts. A new head (every commit with the `Work-issue-plan` trailer) or a new plan starts at attempt 1 as before. The worker never writes the release marker: parking exists so that a person looks at the reason first. Attempt 1 is retried once by the next run; from attempt 2 on `has-work.py` and `orchestrate-issue` treat the branch as parked. No label is set and the issue is not closed. After the marker the checkout goes back as the skill's clean-up and "Back to the starting branch" say; the marker stays the last write to GitHub. If this section cannot be read, write no comment and say in the report that the finish marker is missing and why.
