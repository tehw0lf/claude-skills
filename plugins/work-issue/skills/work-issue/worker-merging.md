## Merging

Merge only when all hold:

- the review of the **current** head has zero `blocking` and zero `fix-in-PR`
- the base branch requires at least one check, and every required check on the head has concluded **green** — not pending, not "failed but probably unrelated". Checks that are not required are neither waited for nor a merge condition, whatever their state. Reason: no merge condition depends on an account posting, or not posting, something; the required checks are named by the repository's own ruleset and enforced by the base branch. The wait for them is short and bounded (the commands below): when the prompt names the required checks and one of them is missing from `gh pr checks --required` or has not concluded when the wait ends, do not merge and do not wait longer, stop with the marker (reason `pending-check`, one sentence naming the checks that had not concluded). Reason: the runs are asynchronous; a check that takes longer than the wait (an installed app once reported ten minutes after the push) is picked up by the next run, which resumes the PR once every required check passes, instead of holding a session open or waiting for a person. When the prompt names no required checks and `gh pr checks --required` reports none (exit 1, "no required checks reported" or "no checks reported"), nothing is known to gate the merge: either the base branch requires none or a required check has not reported yet, and the command cannot tell which. Do not merge, stop with the marker (reason `awaiting-merge`, one sentence saying that no required check has reported on the head)
- the PR has no merge conflicts and the head is still the reviewed SHA
- every required check on the head started after the PR's latest base change (a retarget keeps the head SHA, and a `pull_request` workflow without the `edited` activity type does not run again, so green checks can come from the merge with the old base; checked as described below)
- the PR's base is the default branch (otherwise the change lands in another PR's branch, and the review looked at the diff against that branch), and no open PR in the repository has this PR's head branch as its base (the merge deletes the head branch, and a PR based on it would be closed or retargeted without anybody deciding it)
- every validation command of the skill's step 7 exited 0 locally on that head — a command that could not run is not a pass: report the open PR and what could not run
- the head is not behind the base where the base requires it to be up to date (below)
- every version file that step 6 bumps (those the repository's versioning rule names, otherwise the manifest of the root `MANIFEST` line; only a file that holds a version value counts, a lockfile follows its manifest) holds a version on the head that is above the one on `refs/remotes/origin/<default>`; a repository with no such file is not checked (the check is described below). Reason: two PRs that start from the same base both bump to the same value, and after the first is merged the base merges into the second without a conflict, because both sides made the same change; the second would merge with a version the default branch already has, and no versioned artifact would be produced for it

First the base, each as its own command:

```bash
gh pr view <PR> -R <owner>/<repo> --json baseRefName,headRefName    # baseRefName must equal the default branch
gh pr list -R <owner>/<repo> --base <headRefName> --state open --json number    # must be empty
```

Either condition failing means no merge and a stop with the marker (reason `other`, one sentence naming the base or the dependent PR numbers):

- **Base is not the default branch:** this PR is itself the stacked one. Report that a person decides: merge by hand, or retarget it to the default branch and get a new review, because the existing verdict covers the diff against the other branch while the retargeted diff also holds that branch's commits (the head SHA stays the same, so the verdict would still match it; the `BASE` line of the script below catches a retarget made after the verdict).
- **Dependent PRs exist:** report that a person retargets them to the default branch, or merges by hand, because `--delete-branch` would otherwise close or retarget them.

The check also covers a resumed PR, whose base this run never set; a stacked PR can only come from a person.

**A branch behind its base is updated, not left for a person.** Once the review of the current head is clean and the base checks above have passed (a stacked PR stops there, before anything is written to it), and before the required checks are read, run `git fetch origin`, then `gh pr view <PR> -R <owner>/<repo> --json mergeStateStatus -q .mergeStateStatus`, and check the versions: for every file named in the version condition above read the value on the head (the file in the checkout, which is on the reviewed head) and on the base (`git show refs/remotes/origin/<default>:<path>`; a JSON manifest by its `version` field, `pyproject.toml` by `[project] version`, `Cargo.toml` by `[package] version`, any other file as the repository's rule names it) and compare them component by component as numbers. The worker reads them itself: which files count depends on the repository's versioning rule, which only the session reads. `UNKNOWN` (GitHub is still computing it, as after a change of the base) is read again, a few times over at most a minute; a state that stays `UNKNOWN` is a stop without a marker, like an `unknown` mergeable state, and the next run reads it again. `DIRTY` (the merge commit cannot be created cleanly) leads straight to "A version-only conflict is resolved, not left for a person" below, without an `update-branch` call and before the version check decides anything (a head that conflicts with the base does not contain it). `BEHIND` (the base requires the branch to be up to date and it is not) **or** a checked version that is not above the base's leads to an update; any other state goes on. The second case also occurs on a base that does not require an up-to-date branch, because the squash merge of the second PR is clean for the same reason. Then `git rev-list --count HEAD..refs/remotes/origin/<default>` decides: above 0 (or the state is `BEHIND`), the branch is updated as below; 0 (the head already contains the base, so `update-branch` would have nothing to merge), no update call is made and "A version the base already holds is bumped again" below runs on the current head. Update with the base merged in, never rebased, as its own command:

```bash
gh api -X PUT repos/<owner>/<repo>/pulls/<PR>/update-branch -f expected_head_sha=<reviewed-sha>
```

`expected_head_sha` makes GitHub refuse the update when the head moved after the review. The update itself runs asynchronously: read `gh pr view <PR> -R <owner>/<repo> --json headRefOid -q .headRefOid` again, a few times over at most a minute, until it differs from the reviewed SHA. Then:

- a refusal because of a merge conflict (the base moved between the read and the call) → "A version-only conflict is resolved, not left for a person" below; a conflict that paragraph does not cover stops with the marker (reason `conflict`). Any other refusal → stop with the marker (reason `merge-refused`, one sentence with the reason GitHub gave), both written for the reviewed head
- the head did not move within the minute → stop without a marker and report it: the update may still land, and the next run reads whatever head the PR has then
- the count was 0 and no update was called → the head already contains the base: continue at the version check of the next bullet, with the current head as the new head (the install of step 4 and the record of the untracked entries are those of the run, nothing changed under them)
- the head moved → `git fetch origin`, then as its own command `git merge --ff-only --no-overwrite-ignore refs/remotes/origin/<headRefName>` on the PR branch. A refusal because an ignored local file would be overwritten is the same stop as the refused fast-forward in the skill's "Resume an own PR" (`resume.md`) (the marker reason `other` under "Stop marker", the paths in the report, the file neither moved nor deleted); any other refusal is reported and stops the run without a marker, nothing reset. Check that `git rev-parse HEAD` equals the new head. Record the untracked entries again into `status-after-switch.txt`, with the command of the skill's "Resume an own PR" (`resume.md`) (the base may have changed an ignore rule, and step 7 must not take a file that was there before for validation output), run the install of the skill's step 4 again (the base may have changed manifests or lockfiles, and step 4 installs only once), then the version check on the new head as above and "A version the base already holds is bumped again" below (a version above the base's goes on; equal bumps again; below the base's stops), then the full validation of step 7 (on a re-bumped tree with the form (a) restore of step 7 for every path of the bump list). A failing command is not fixed here: stop with the marker (reason `other`, one sentence naming the command that fails on the head with the base merged in); a command that cannot run stops with the marker (reason `not-runnable`). Then get a review round of the new head as in "Independent review": a fresh reviewer without a model override, told about the earlier rounds and that the new head merges the base into the reviewed head and, where it applies, bumps the version again (the file, from and to) or resolves a version-only conflict (the files, the PR's, the base's and the new values). This round is not bound by the limit of 4, like the `BASE` round below; its `blocking` and `fix-in-PR` findings are handled as under "Independent review". Then every merge condition is checked again for the new head, from the base checks on, including a second `mergeStateStatus` read and a second version check.

**A version the base already holds is bumped again.** This runs on a head that contains the base, from the line above. Read the values as above for every checked file. Above the base's: nothing to do. Below the base's (the bump of this skill cannot produce that): stop with the marker (reason `other`, one sentence naming the file and both versions). Equal to the base's: bump again, by step 6 as written for a run in which the change touched no file on purpose. First put the tracked changes back to `HEAD` (the install of step 4 may have rewritten a lockfile), then take the two snapshots, run the bump command and the lockfile sync (they start from the head's value, which equals the base's, so a patch bump lands above it), apply the tests for a tracked lockfile and the stops for quoted paths of step 6, and note the bump list. No bump patch is saved: there is no change commit to separate it from. Step 7 then runs on that tree with form (a) for every path of the bump list, so that the tree validated is the tree pushed. Only after a green validation is the bump committed, as step 8 (d) alone (the bump's files and the entries the version scripts produced, explicit `:(literal)` arguments), with a conventional-commit subject and without the `Work-issue-plan` trailer, and pushed with a plain `git push`, never forced. The commit is a later commit on an existing PR, like the commit of a review fix; step 8's rule that the version is not bumped a second time concerns review fixes and does not cover replacing a version the base already holds. A failing command or one that cannot run stops with the marker as above, after the bump is undone in the tree (`git restore -- ':(literal)<path>' …` for the bump list, `git clean -f -- ':(literal)<entry>' …` for the recorded version-script entries and for a lockfile that step 6 noted as not tracked): a failure then leaves no unpushed commit, and "Back to the starting branch" finds a clean tree. After the push, correct the PR body where it names the version and read it back with `gh pr view <PR> -R <owner>/<repo> --json body -q .body`. The reviewer of the next round is told what the bump changed.

At most one update per run: the re-bump and the resolution of a version-only conflict are each that one update, and a version that is still not above the base's at the second check, like a head that is `BEHIND` or `DIRTY` again at that second read, stops without a marker, and the report says that the base moved again during the run. Nothing is wrong with the PR, and a marker would park it for a person; without one the next run resumes it, finds the review of the new head and updates once more. Reason for the update: with a base that requires an up-to-date branch, every merge into the default branch leaves every other open PR behind it, and a PR that waits for a person each time does not get merged unattended. A merge commit instead of `--rebase` keeps the push a fast-forward, so no reviewed commit is rewritten and the squash merge lands the same change; the new head is reviewed and checked like any other, so nothing unreviewed is merged. The checks of the new head often report later than the bounded wait, which ends in `pending-check` and the next run.

**A version-only conflict is resolved, not left for a person.** Two PRs from the same base that both bump the version conflict in that line whenever their values differ, and `update-branch` cannot resolve a conflict; leaving each one for a person defeats unattended merging. Entered from `DIRTY` at the first `mergeStateStatus` read or from a refused `update-branch` because of a conflict, it changes nothing but version values, and the result is validated and reviewed like any other head. It runs only when every precondition holds; a failing one leads to the abort path below.

1. The start: `git rev-parse HEAD` equals the reviewed SHA and `git status --porcelain` is empty. Otherwise stop without a marker and report; nothing is discarded.
2. `git fetch origin`, then as its own command `git merge --no-ff --no-commit --no-overwrite-ignore refs/remotes/origin/<default>`. A refusal because an ignored local file would be overwritten is the stop of the fast-forward in the bullet above (marker reason `other`, the file neither moved nor deleted); no merge was started, so nothing is aborted.
3. Preconditions, checked on the unmerged state:
   - every unmerged path (`git -c core.quotePath=false ls-files -u`) is a file that step 6 bumps (as in the version condition above) or the lockfile that step 6 syncs for such a manifest; a path that contains `'` or starts with `"` is not put into a command (the rule on paths taken from printed output) and fails this precondition
   - each such path has all three stages (1 base, 2 ours, 3 theirs); a delete or rename conflict lacks one
   - inside every conflict hunk the ours and theirs sections have the same number of lines and differ, line by line, only in the version value; a `|||||||` section (`diff3` style) is ignored
   - for each file that step 6 bumps the three values (`git show :1:<path>`, `:2:`, `:3:`, read as above) are plain `X.Y.Z`, stage 2 is above stage 1 (the PR's bump) and stage 3 is above stage 1 (the base's bump)
   - for an npm root, the `jq` read of `preversion`, `version` and `postversion` from step 6 prints `{}`: a version script may move further files, which a resolution by hand would miss
4. The new value of each file is its stage 3 value (the base's) with the patch raised by one, computed per file. Whether another open PR already holds that value is not visible here; the version check catches that when the other PR merges first.
5. Each hunk, markers included, is replaced with the Edit tool by its theirs lines with the base value replaced by the new value; then `git add -- ':(literal)<path>'` for each path. A tracked lockfile is resolved by the same rule, then the lockfile sync of step 6 runs, and afterwards `git diff --name-only` and `git ls-files -u` must both print nothing: the sync has to agree with the resolution by hand.
6. `git commit --no-edit` keeps git's merge message, as the merge commit of `update-branch` does, and carries no `Work-issue-plan` trailer: like the re-bump above it is a later commit on an existing PR, and the same sentence on step 8's rule covers it.
7. A plain `git push`, never forced; it is a fast-forward because the reviewed head is the first parent. Then read `gh pr view <PR> -R <owner>/<repo> --json headRefOid -q .headRefOid` a few times over at most a minute until it equals `git rev-parse HEAD`.
8. Continue in the bullet "the head moved" above from "Check that `git rev-parse HEAD` equals the new head": the record of the untracked entries, the install, the version check (the resolved value is above the base's, so no re-bump follows), the full validation with its stops, the review round and the corrected PR body, read back as for the re-bump.

**Abort path:** when a precondition fails, `git merge --abort` runs as its own command, then `git rev-parse HEAD` must equal the reviewed SHA and `git status --porcelain` must be empty, and the run stops with the marker (reason `conflict`, one sentence naming the conflicting files) for the reviewed head. A check that fails after the abort is reported and the marker stays as it is. When the local merge has no conflict at all (GitHub said `DIRTY` but git merges cleanly), the merge is aborted the same way and the run stops without a marker: nothing is known to be wrong, and the next run reads the state again. Failures after the commit stop without a marker and the local commit stays: a rejected push (as for a review fix whose push was rejected) and a PR head that does not reach the pushed commit within the minute.

**If a required check is red, stop and report — do not merge** (marker reason `red-check`). Judging a failure "unrelated" is not your call: a scan can go red from a vulnerability-database refresh, and only a person decides to merge past that. Report the failing check and your reading of the cause.

```bash
gh pr checks <PR> -R <owner>/<repo> --required    # a named check missing here has not reported: stop with pending-check now, a watch cannot see it
timeout 300 gh pr checks <PR> -R <owner>/<repo> --required --watch    # only while a listed check is pending; at most five minutes (exit 124: the time ran out)
gh pr checks <PR> -R <owner>/<repo> --required    # confirm: every check pass goes on; fail or cancel stops with red-check, skipping with awaiting-merge (a person decides whether a skipped required check is enough), missing or pending with pending-check when the prompt names the required checks, else with awaiting-merge
gh pr checks <PR> -R <owner>/<repo>    # once, for the report only: name each check that is not required and red or still pending; the exit code (0, 1 for a failed check, 8 for a pending one), the empty result and a failure without a listing are handled as below the block, none changes the merge decision
gh pr view <PR> -R <owner>/<repo> --json headRefOid -q .headRefOid    # must equal the reviewed SHA
```

Run the `timeout 300` watch with the Bash tool's own `timeout` parameter set to `330000` (milliseconds): the tool ends a call after 120 seconds by default, which would cut the wait short. A watch that ends without its own exit code (the tool stopped it) counts like exit 124: the confirming listing after it decides.

The report-only call (without `--required`) prints a listing of the checks on stdout, and its exit code does not say whether the call worked: 0 when all pass, 1 when a listed check failed, 8 when one is pending. Read the listing for the report whatever the code is (a red or pending check that is not required is what the call is for). Exit 1 with nothing on stdout and `no checks reported on the '<branch>' branch` on stderr means that no check of any kind has reported on the head: the report says "no checks reported on the head"; it is not an error and not a reason to stop. Any other failure without a listing (for example a GraphQL error for an unknown PR, also exit 1) is reported as "checks that are not required could not be read", with the message `gh` gave; it is no reason to stop either. Reason: exit 1 covers a failed check, the empty result and a real error alike, so only the stdout listing and the stderr message tell them apart; checks that are not required are no merge condition (first list, second item), so no outcome changes whether the worker merges or stops. In a repository without any checks the `--required` call above already ends the run (`awaiting-merge`, or `pending-check` when the prompt names the required checks); this rule only applies where the report call is still run, for example for the report of that stop, and is not a second gate.

Then read the verdict and base facts. This is the last check before the merge, after the required checks are green. `<skill directory>` is the `work-issue` skill directory named in the first line of the preloaded skill.

```bash
<skill directory>/scripts/merge-facts.py <owner>/<repo> <PR>
```

It prints the latest verdict of this account (`VERDICT`, with the head it reviewed), the current head (`HEAD`), one `BASE` line (created time, previous base, current base) for each change of the PR's base branch at or after the verdict, and, whatever the verdict, one `LASTBASE` line (created time) for the newest base change of the whole timeline (none when the base never changed). Act on the result:

- exit code other than 0 or a `SKIPPED` line → report, no merge: a source that could not be read leaves the condition unverified
- the `VERDICT` head differs from the reviewed SHA → report, no merge
- `BASE` lines → the latest verdict was made against the diff of another base, and it binds only the head, so the retargeted PR passes a head comparison with a review that never saw its current diff. Get a further review round as in "Independent review": a fresh reviewer without a model override, told about the earlier rounds and that the base changed after the previous verdict (from, to), so that it reviews the current head against the current base as a whole. It is not bound by the limit of 4 rounds; each further round needs another retarget. The worker opens every PR against the default branch, so only a person causes a base change, just as only somebody else's push or the worker's own branch update causes the resume round that is exempt in the same way. Its `blocking` and `fix-in-PR` findings are handled as under "Independent review" (stop, or fix and push). The same holds on a resumed PR (see "Resuming an own PR" for the limit). Afterwards check all merge conditions again for the new verdict, including this script
- a `LASTBASE` line → the required checks must postdate it. Read their names with `gh pr checks <PR> -R <owner>/<repo> --required --json name` and their start times with `gh pr view <PR> -R <owner>/<repo> --json statusCheckRollup` (`startedAt` of each entry, matched by `name` for a check run or `context` for a commit status; its `startedAt` is the time it was created, whereas `gh pr checks --json startedAt` reports the zero date for it) and stop with the marker (reason `other`, one sentence naming the checks that predate the base change) when any required check's `startedAt` is before or equal to the `LASTBASE` time, or is empty, unreadable, missing from the rollup or the zero date `0001-01-01T00:00:00Z` (unverified): that check ran, or may have run, against the merge result of the old base. The line stays after the `BASE` round and in every later run, because it ignores the verdict. Every required check counts, also one that does not depend on the base. Only a person decides how to get checks on the current base (a new event, or a manual merge). The condition applies again after each round above, with the script run again.

Windows stay open. A retarget between the reviewer's last read of the base and the posting of the verdict is caught by nothing. A required check that has not reported yet is not listed by `--required`, so the wait cannot see it (`orchestrate-issue` closes this by naming the required checks in the worker's prompt, and a named check that is missing ends the run with `pending-check`). Three cases of the check-start rule stay open, because `startedAt` is when a job started or a status was last posted, not when its event happened: a run triggered before the retarget whose jobs only start after it (waiting for a runner or in a concurrency group), and a re-run after the retarget, which keeps its original event, and an external check that started before the retarget and posts its result as a commit status afterwards (the status's `startedAt` is the time of its last state). All three pass the rule although they may have tested the old base. And a person can retarget the PR in the seconds between this script and the merge; `--match-head-commit` covers the head only, not the base (the base check above runs earlier).

Right before it, run `git fetch origin`, read `gh pr view <PR> -R <owner>/<repo> --json mergeStateStatus -q .mergeStateStatus` once more and repeat the version check: the base can move during the check wait and the script. `BEHIND` or `DIRTY` there, or a version that is not above the base's, is a stop without a marker, and the report says that the base moved after the checks; the next run resumes the PR and updates it (a branch update made in this run still counts as the one per run). Then, as one plain command — not in a loop or a compound command:

```bash
gh pr merge <PR> -R <owner>/<repo> --squash --delete-branch --match-head-commit <reviewed-sha>
```

`--match-head-commit` makes the merge fail if the head moved after the review, so nothing unreviewed can ride along. A merge that is refused (a missing token scope for workflow files, branch protection) is reported with its message, not worked around. A refusal because the head is not up to date with the base (the base moved in the seconds after the last read) is a stop without a marker, like `BEHIND` above; any other refusal stops with the marker (reason `merge-refused`).

After the merge, check that the issue is closed and, where the default branch runs a pipeline on push, report that run's state without waiting longer than it normally takes. Then the checkout goes back as under "Back to the starting branch".
