# Cross-repository coupling

Which files rely on each other. `CLAUDE.md` lists the files; this file says what each side depends on. A change to one of them is made together with the other side: in the same PR where both are in this repository, otherwise after checking the other repository.

- `setup-workflows` is bound to `tehw0lf/workflows` (checked out at `../../workflows`): the orchestrator path `.github/workflows/build-test-publish.yml`, its `workflow_call.inputs` block, and the fact that it only calls other workflows by `./` reference. `fetch-permissions.py` exits on any other kind of reference on purpose — extend the script when that changes, do not skip the reference. `validate-caller.py` expects the caller at `.github/workflows/build.yml` and finds the job by its `uses:`, not by name.
- `prune-branches all` (`classify.sh --all`, also `classify.sh` with no argument outside any repository) scans `$CODING_ROOT` (default `~/Nextcloud/Coding`) for repositories up to two directory levels below it and reads keep rules from `$XDG_CONFIG_HOME/prune-branches-keep` and `.git/prune-branches-keep`.
- `work-issue` depends on `pr-review` at run time: `issue-worker` spawns `pr-review:pr-reviewer` for every review round and does not merge when that agent type is missing. The skill alone (up to the open PR) needs no other plugin. `issue-context.py` reads one issue through `gh api graphql`, the permission of comment authors through `repos/<o>/<r>/collaborators/<login>/permission` (bots are not looked up: that endpoint does not know them) and the checkout it is run in; `SKILL.md` relies on its line kinds (`ISSUE`, `CHECKOUT`, `ACCOUNT`, `PR`, `RESUME`, `PLAN`, `QUESTIONS`, `BRANCH`, `PUSHED`, `WORKTREE`, …) and on the names of its `# SKIPPED` sources. Planner, worker and script share one comment format: the first line `<!-- work-issue:plan base=<sha> -->` (or, for a plan that adopts an own PR or pushed branch of an earlier plan, `<!-- work-issue:plan base=<sha> adopts=<plan comment id> -->`, written only as `adopt.md` beside the `plan-issue` `SKILL.md` says, which belongs to this shared format; `issue-context.py` prints the id as the 7th `PLAN` field only when it is the id of an earlier plan comment of `ACCOUNT`, else `-`; `has-work.py` `parked()` requires exactly 7 fields; `print_resume` prefers the current plan id, then the adopted one, then the first link) or `<!-- work-issue:questions -->`, written by the `ACCOUNT` login (an issue marker `<!-- work-issue:closed -->` is written only by `plan-issue` on a close; `issue-context.py` deliberately counts it as an ordinary comment, so a reopened issue gets a planner run, which asks again; a marker `<!-- work-issue:finish-stopped branch=<branch> head=<full sha> plan=<plan comment id> attempt=<n> reason=<kind> -->` goes on the issue and is the one write to an issue that `issue-worker` makes (`worker-stop-marker.md`, "Finish marker", on a stop in finish mode before the PR exists): `issue-context.py` treats it as a marker like plan and questions (it neither answers questions nor makes the plan stale) and prints it as a `FINISHSTOP` line per branch (newest of `ACCOUNT`; `answered` only after a release marker, see below), and `has-work.py` and `orchestrate-issue` step 3 compare it with `PUSHED` and `PLAN`; a release marker `<!-- work-issue:finish-released branch=<branch> head=<sha> plan=<plan comment id> -->` is written by a person with write access, by hand (`gh issue comment`; no agent writes it), and `issue-context.py` treats it as a marker like plan and questions (no answer, no owner comment, so the `PLAN` stays current): it is the only thing that sets `FINISHSTOP … answered`, and only when it comes after the finish marker, names the same branch and plan, has a head equal to the finish marker's by prefix in either direction and its author is `is_trusted` true; a plain comment of a writer sets nothing here and makes the `PLAN` stale instead; `worker-stop-marker.md` ("Finish marker") and `orchestrate-issue` step 3 (which prints the release line in the parked report) carry the same format; a further marker, `<!-- work-issue:stopped head=<sha> reason=<kind> -->`, goes on the PR, not the issue: `issue-worker` writes it when it stops after the PR exists, and `issue-context.py`'s `RESUME` line reads it, together with the newest `## Independent local review` verdict and whether an account with write permission commented after the marker; the PR body names the plan as the full link `https://github.com/<owner>/<repo>/issues/<n>#issuecomment-<id>` outside code, which `work-issue` step 8 writes and `print_resume` matches; every commit of a run's branch carries the trailer line `Work-issue-plan: https://github.com/<owner>/<repo>/issues/<n>#issuecomment-<id>`, which step 8 writes and `plan_from_messages` in `issue-context.py` reads for the plan field of the `PUSHED` line, which `finish-branch.md` and `orchestrate-issue` step 3 compare with the `PLAN … current` id or the id it adopts; `PUSHED` is a line kind of its own so that readers of `BRANCH` stay valid; a branch that is or was the head of any pull request of the repository, open, closed or merged, gets no `PUSHED` line, because the branch of a closed or squash-merged PR is not an aborted run's); the script counts only such comments of that login as plan or questions, and only comments of accounts with admin, maintain or write permission as answers (anyone can comment on an issue, so a forged plan must not steer the worker; `author_association` is not used because it says nothing about permission). `issue-context.py --comments` is what planner and worker read instead of `gh issue view --json comments`: it prints only comments of `ACCOUNT` and of such accounts and counts the rest as `OMITTED`. The same test applies to the text of `PR` and `REF` lines: head branch and title are `-` unless the author of that pull request or issue is `ACCOUNT` or has such a permission (anyone can open one); number, state and relation stay, so the stop conditions do not depend on it. Each kind (plan, questions, stop marker, verdict) also carries a visible italic origin line below its heading, or directly below the marker when there is no heading, never as line 1; the scripts do not read it. Change the format in `plan-issue`, `work-issue`, `issue-worker`, `issue-context.py` and `scripts/issue-stats.py` together.
- `nx-migrate` depends on `pr-review` at run time the same way: `nx-migrator` spawns `pr-review:pr-reviewer` for every review round and does not merge when that agent type is missing. The skill alone (up to the open PR) needs no other plugin.
- `orchestrate-issue` (`has-work.py`) depends on the `QUESTIONS` line of `issue-context.py` (the last field `open` or `answered`) and its `# SKIPPED account|plan|comments` lines (`permission` no longer fails the check), its `PUSHED` and `FINISHSTOP` lines (a branch is parked when `PUSHED` carries the `PLAN … current` id or the id it adopts and `FINISHSTOP` has the same branch, head by prefix and plan with attempt 2 or more and no `answered`, meaning not released by a release marker; the writer is `issue-worker`, see the `work-issue` entry; step 3 compares the `PUSHED` and `RESUME` plan fields with the id of a `PLAN … current` line and the id it adopts: any other value that is not `-`, including the id of a stale `PLAN` line, goes to the planner when the plan is stale or missing (which adopts the branch or PR or asks with `needs-decision`, `adopt.md`) and is reported without a planner when the plan is current; `has-work.py` makes the same split: such a line with a current plan is no hit, with a stale or missing one a hit), its `RESUME` line (head, mergeable state, stop marker head, reason and `answered`; the reason `pending-check` written by `issue-worker` is released once every required check passes, or at once when the mergeable field is `conflicting`) and on the label `needs-decision` that `plan-issue` sets and removes; for `pending-check` it reads the required checks like `run-context.py` (`repos/<o>/<r>/rules/branches/<default>`, `repos/<o>/<r>/branches/<default>`) and `gh pr checks --required --json name,bucket`; it runs `issue-context.py` by the relative path `../../work-issue/scripts/`. Step 4 posts an owner's chat answer as an issue comment and relies on `issue-context.py` counting an unmarked comment by `ACCOUNT` after the questions comment as the answer (`QUESTIONS … answered`) and on `plan-issue` step 3 reading the newest trusted comment as the answer, so the copied answer stays first and verbatim and the origin line last. For `--owner <login>` it reads `users/<owner>` and `search/issues` with `user:<login>`, as `run-context.py` does; both depend on the search result fields `items`, `total_count`, `incomplete_results`, `repository_url`, `number`, `labels` (`has-work.py`) and on `user:` matching organisations too. `dispatch.py` depends on the `WORK`/`ERROR`/`NONE` lines and exit codes of `has-work.py --all` (same directory), on `systemd-escape --template` for the instance name and on `systemctl --user list-units` (first column, the unit name) and `systemctl --user start --no-block`; the template units in `scheduling.md` rely on `%I` giving the repository back.
- `orchestrate-issue` (`run-context.py`) depends on `$CODING_ROOT` (same scan as `classify.sh --all`), `gh repo clone`, the line kinds of `issue-context.py` and `run-context.py`, the GraphQL query `issue.userContentEdits` with `createdAt` and `includesCreatedEdit` (the edit check: any edit by a non-writer, whenever made, makes the issue untrusted; the revision that records the creation is not an edit) and the endpoints `users/<owner>`, `search/issues` (for `--owner`), `repos/<o>/<r>/rules/branches/<default>`, `repos/<o>/<r>/branches/<default>` (classic protection), `repos/<o>/<r>/issues/<n>/events` and `repos/<o>/<r>/collaborators/<login>/permission`.
- `propose-auto-work` (work-issue) depends on the line kinds of `issue-context.py` (`ISSUE`, `ACCOUNT`, `PR`, `RESUME`, `QUESTIONS`, `PLAN` and the `# SKIPPED` sources `query`, `labels`, `assignees`, `account`, `pull-requests`, `comments`, `plan`) run outside any checkout, on those of `run-context.py` (`REPO`, `CHECKS`, `CHECKOUT`, and `ISSUE` with labeler, permission and `edit` in label mode), on the label `needs-decision` that `plan-issue` sets, on the endpoints `repos/<o>/<r>/collaborators/<login>/permission` and `repos/<o>/<r>/labels/auto-work`, and on the labeler rule of `orchestrate-issue` step 1 (labeler and permission not `-`, permission `admin`, `maintain` or `write`, `edit` `none` or `trusted`, neither `untrusted` nor `-`). A change of that rule is made in both skills. It is the only place that sets `auto-work`.
- `inbox` (`collect.py`) reads every non-archived, non-fork repository of the owner through `gh` (`--owner <login> --contributed [N]` instead reads the GraphQL field `viewer.repositoriesContributedTo` (`includeUserRepositories: true`, `contributionTypes: [COMMIT, ISSUE, PULL_REQUEST, PULL_REQUEST_REVIEW]`, `orderBy: {field: PUSHED_AT, direction: DESC}`, pages of 100), which has no owner argument: the owner match (case-insensitive) and the archived and fork filters run in the script, pages are read until N repositories were kept, and the header gets a `contributed=<N>` key after `scope=`; the search stays `user:<owner>`, so only rows of the listed repositories are shown; a fatal `gh` error names its query as `repositories`, `contributed`, `repository` or `search`; `tests/test_collect.py` covers this mode with a fake `gh`, so a change of the query or of these names changes the fake and the fixture in `tests/fixtures/collect/` too; `--repo` / `--here`: one repository, live, no cache and no lock; `--here` resolves it with `gh repo view` in the current directory and exits 2 when there is none, which the skill takes as the cue for the account-wide list; the header's `scope=` key says which was read). The default run, when the owner is the `gh` login, adds those of every organisation in `viewer { organizations(first: 100) }` (needs the `read:org` scope; an `<org>/*` ignore line keeps an organisation from being queried; the header's `owners=` key lists the owners read, a cache file from before has none and `--summary` falls back to `owner=`; an unreadable organisation becomes a `# SKIPPED` line, `repos=0` a `# NOTICE` line). It keeps one merged cache, `inbox-<owner>.tsv` for the owner the default run resolved to (`--owner <name>` writes none), plus `default-owner`, `refresh.lock` and `refresh.error` in `$XDG_CACHE_HOME/claude-inbox/` and reads ignore rules from `$XDG_CONFIG_HOME/inbox-ignore`. The `RUN` rows come from one `gh api repos/<o>/<r>/actions/runs?branch=<default>&per_page=100` call per repository (fields `status`, `conclusion`, `event`, `path`, `name`, `display_title`, `head_sha`, `created_at`, `html_url`, `head_repository.full_name`; the head commit's `oid` comes from the GraphQL query), and Dependabot update jobs are told apart by the shapes of `display_title` (`<ecosystem> in <dir> - Update #<id>`, `<ecosystem> in <dir> for <deps> - Update #<id>`, `Graph Update: <ecosystem> in <dir> #<id>`, and the same cut off after the dependency list): a title of none of these shapes is keyed by its workflow path, and a change of GitHub's title text splits or merges rows, and a change of a repository's Dependabot directory list splits rows the same way and leaves the old title's last red run as a `RUN` row. Dependabot alerts that are switched off are read from the GraphQL field `hasVulnerabilityAlertsEnabled`: the administered repositories (`viewerCanAdminister`) with it false are counted into one `# SKIPPED dependabot` line per owner (per repository under `--repo`/`--here`), next to the existing line for repositories without admin permission. Its SessionStart hook only ever reads the default owner's cache and starts a detached `--background` refresh when it is stale, so a session start never waits for GitHub; the lock keeps refreshes from overlapping, and a failed background refresh is shown by the next summary; the hook prints JSON, and its line format is not parsed anywhere. Step 4 hands a picked `ISSUE` item to `work-issue:work-issue` when the session lists that skill and falls back to working it by hand otherwise, so the coupling is optional. Every row carries two more columns after `url`, `assignees` and `closing` (`-` for every kind but `ISSUE`), read from the GraphQL fields `assignees` and `closedByPullRequestsReferences(includeClosedPrs: false)` of `... on Issue`; nothing parses them but the skill (the hook reads only the kind column), so older cache files stay valid. Step 4 also groups the `ISSUE` rows without assignee, closing PR, `needs-decision` and `auto-work` label as auto-work candidates and hands a picked subset to `work-issue:propose-auto-work` when the session lists it; the coupling is optional the same way.
- `check-install-config.py` exists in `nx-migrate` (steps 1 and 2) and in `work-issue` (step 5) as byte-identical copies, because a skill calls only scripts of its own plugin and each skill works without the other plugin. A change to the script, its line kinds or its list goes into both copies in the same PR, bumps both plugins, and updates both `SKILL.md` files where they rely on the output; the `cmp` line under Commands in `docs/commands.md` checks it.
- `merge-facts.py` exists in `work-issue` and in `nx-migrate` as byte-identical copies, for the same reason as `check-install-config.py`. Each copy is called by its plugin's agent (`worker-merging.md` of `work-issue` and `nx-migrator.md` under Merging), and both agents rely on its line kinds (`VERDICT`, `HEAD`, `BASE`, `LASTBASE`, `SKIPPED`). A change goes into both copies and both agents in the same PR and bumps both plugins; the `cmp` line under Commands in `docs/commands.md` checks the copies. The script also depends on the verdict heading `## Independent local review` and the `Reviewed head:` line of `plugins/pr-review/agents/pr-reviewer.md`: a renamed heading leaves it with `SKIPPED verdict` and no merge. The `BASE` lines come from the PR timeline through `gh api graphql` (`timelineItems` with `itemTypes: [BASE_REF_CHANGED_EVENT]`, fields `createdAt`, `previousRefName`, `currentRefName`; completeness is checked against `filteredCount`, not `totalCount`, which counts events of every type): the verdict binds only the head, so a retarget after the review is otherwise invisible. `LASTBASE` is the newest base change regardless of the verdict, because after the round a `BASE` line causes, the verdict is newer than the change and no `BASE` line is printed any more; the agents compare it with the start time of the required checks only (names from `gh pr checks --required`, start times from `statusCheckRollup`) and refuse the merge while any of them started before it (a retarget keeps the head SHA and a `pull_request` workflow without the `edited` type does not run again), `issue-worker` with a stop marker of reason `other`, `nx-migrator` with a report (#189). A `BASE` line makes the agents run one further review round on the current head (not bound by the limit of 4: only a person retargets a PR). The reviewer reads `baseRefName` at the start and again just before the verdict and repeats its base-dependent checks when it changed (`pr-reviewer.md`, "Verdict"; this paragraph depends on that rule); a retarget between the reviewer's last read of the base and the posting of the verdict is older than the verdict and caught by nothing. A resume round on a head without verdict is not bound by the limit of 4 when the PR already has four or more verdicts: only somebody else's push or `issue-worker`'s own branch update (`update-branch` on a branch behind its base) creates such a head. No merge condition depends on what an account posts after the verdict: the agents handle automated reviewers nowhere (#225).
- `repo-commands.py` (work-issue only, not shared with `nx-migrate`) composes the commands of a caller of `build-test-publish.yml` exactly as `test-and-build.yml` of `tehw0lf/workflows` runs them (`<tool> <input>` for install, format, lint, test, e2e and build_branch; `npm` always `npm ci`, `yarn` always `yarn install --frozen-lockfile`; `cargo` additionally `cargo fmt --all -- --check` and `cargo clippy --all-targets ...`; no commands for `tool` absent or `none`). A change in how that workflow composes or defaults these steps is mirrored in the script's docstring and code in the same PR. `work-issue` `SKILL.md` steps 4 to 7 rely on its line kinds (`CALLER`, `CI`, `TOOLCHAIN`, `SCRIPT`, `MAKE`, `PROJECT`, `DOC`, `WORKFLOW`, `FALLBACK`, `SKIPPED`). A new fallback row goes into the docstring and the code (not into `SKILL.md`), only after its commands were run against the real tool.
- `scripts/review-rounds.py` depends on the verdict layout of `plugins/pr-review/verdict-layout.md` (the agent reads it before it writes the verdict) and on the fixed lines that `plugins/pr-review/agents/pr-reviewer.md` repeats, which also give the flat fallback used when the file cannot be read: the first line `## Independent local review` (a comment with any other first line is not counted, so a renamed heading turns every new verdict into a `NOVERDICT` line without a warning), the count line `**Blocking: <n> · Fix in PR: <n> · Follow-up: <n>**` and, for verdicts without the count line (the flat layout before #31), the `### Blocking`, `### Fix in PR` and `### Follow-up` headings. - `scripts/issue-cost.py` reads the local session transcripts, an undocumented format: per line `type`, `isMeta`, `timestamp`, `version`, `gitBranch`, `attributionAgent`, `message.role`, `message.content` (the first user message is the prompt), `message.id`, `message.model` and `message.usage` (the four token fields, `cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`, `speed`, `service_tier`, `inference_geo`); per subagent the `agent-<id>.meta.json` fields `agentType` and `parentAgentId`. A renamed token, id, model or cache breakdown field is reported as `# SKIPPED fields` or leaves a row unpriced; a missing or renamed `speed`, `service_tier` or `inference_geo` counts as standard and is priced without a note; there is no version check. It matches transcripts to issues by the two forms it accepts in a spawn prompt (`owner/repo#n`, `#n in owner/repo`; the spawn sites write only `owner/repo#n`, once per prompt, and name any other issue or pull request as `#m` or `PR #m`, because the matcher takes a prompt only when it yields exactly one reference: `orchestrate-issue` steps 4 to 6 (the rule is stated in step 4), `work-issue` step 1 "The plan", `propose-auto-work`, `issue-planner.md` and `issue-worker.md`; `#n in owner/repo` stays accepted for older transcripts, and a change of the form changes the matcher and these sites together), by the reviewer's `parentAgentId` (`issue-worker.md` gives the reviewer a PR and the repository, not the issue) and by the `<type>/<n>-` branch names of `work-issue`; a spawn prompt that names the issue in another form leaves the file unmatched. Its `ISSUE` rows have the same two key columns (`<owner/repo>` and `<n>`) as the `ISSUE` lines of `scripts/issue-stats.py`, but the repository is lowercased, so a join compares it case-insensitively (`scripts/issue-report.py` does that). It prints one `SESSION` line per transcript file it read in the range (session id, matched issue or `-`, messages added), where the session id is the file name without `.jsonl` or, for a subagent file, the name of the session directory; `scripts/issue-report.py` reads them to notice the same session in the output of two machines. `scripts/issue-cost-prices.json` is a dated copy of Anthropic's public list prices (`as_of`, `source`) and goes stale; the model ids are the values of `message.model`, and a model missing from it is reported, not priced.
- `tests/test_issue_cost.py` and its fixtures in `tests/fixtures/issue_cost/` depend on the output lines of `scripts/issue-cost.py` (`TOKENS`, `ISSUE`, `UNMATCHED`, `SESSION`, the three `# SKIPPED` kinds) and the transcript fields above.
