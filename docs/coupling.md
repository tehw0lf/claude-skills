# Cross-repository coupling

Which files rely on each other. `CLAUDE.md` lists the files; this file says what each side depends on. A change to one of them is made together with the other side: in the same PR where both are in this repository, otherwise after checking the other repository.

- `setup-workflows` is bound to `tehw0lf/workflows` (checked out at `../../workflows`): the orchestrator path `.github/workflows/build-test-publish.yml`, its `workflow_call.inputs` block, and the fact that it only calls other workflows by `./` reference. `fetch-permissions.py` exits on any other kind of reference on purpose — extend the script when that changes, do not skip the reference. `validate-caller.py` expects the caller at `.github/workflows/build.yml` and finds the job by its `uses:`, not by name.
- `prune-branches all` (`classify.sh --all`, also `classify.sh` with no argument outside any repository) scans `$CODING_ROOT` (default `~/Nextcloud/Coding`) for repositories up to two directory levels below it and reads keep rules from `$XDG_CONFIG_HOME/prune-branches-keep` and `.git/prune-branches-keep`.
- `work-issue` depends on `pr-review` at run time: `issue-worker` spawns `pr-review:pr-reviewer` for every review round and does not merge when that agent type is missing. The skill alone (up to the open PR) needs no other plugin. `issue-context.py` reads one issue through `gh api graphql`, the permission of comment authors through `repos/<o>/<r>/collaborators/<login>/permission` (bots are not looked up: that endpoint does not know them) and the checkout it is run in; `SKILL.md` relies on its line kinds (`ISSUE`, `CHECKOUT`, `ACCOUNT`, `PR`, `RESUME`, `PLAN`, `QUESTIONS`, `BRANCH`, `WORKTREE`, …) and on the names of its `# SKIPPED` sources. Planner, worker and script share one comment format: the first line `<!-- work-issue:plan base=<sha> -->` or `<!-- work-issue:questions -->`, written by the `ACCOUNT` login (an issue marker `<!-- work-issue:closed -->` is written only by `plan-issue` on a close; `issue-context.py` deliberately counts it as an ordinary comment, so a reopened issue gets a planner run, which asks again; a further marker, `<!-- work-issue:stopped head=<sha> reason=<kind> -->`, goes on the PR, not the issue: `issue-worker` writes it when it stops after the PR exists, and `issue-context.py`'s `RESUME` line reads it, together with the newest `## Independent local review` verdict and whether an account with write permission commented after the marker; the PR body names the plan as the full link `https://github.com/<owner>/<repo>/issues/<n>#issuecomment-<id>` outside code, which `work-issue` step 8 writes and `print_resume` matches); the script counts only such comments of that login as plan or questions, and only comments of accounts with admin, maintain or write permission as answers (anyone can comment on an issue, so a forged plan must not steer the worker; `author_association` is not used because it says nothing about permission). `issue-context.py --comments` is what planner and worker read instead of `gh issue view --json comments`: it prints only comments of `ACCOUNT` and of such accounts and counts the rest as `OMITTED`. The same test applies to the text of `PR` and `REF` lines: head branch and title are `-` unless the author of that pull request or issue is `ACCOUNT` or has such a permission (anyone can open one); number, state and relation stay, so the stop conditions do not depend on it. Each kind (plan, questions, stop marker, verdict) also carries a visible italic origin line below its heading, or directly below the marker when there is no heading, never as line 1; the scripts do not read it. Change the format in `plan-issue`, `work-issue`, `issue-worker` and `issue-context.py` together.
- `nx-migrate` depends on `pr-review` at run time the same way: `nx-migrator` spawns `pr-review:pr-reviewer` for every review round and does not merge when that agent type is missing. The skill alone (up to the open PR) needs no other plugin.
- `orchestrate-issue` (`has-work.py`) depends on the `QUESTIONS` line of `issue-context.py` (the last field `open` or `answered`) and its `# SKIPPED account|plan|comments` lines (`permission` no longer fails the check), its `RESUME` line (head, stop marker head, reason and `answered`; the reason `pending-check` written by `issue-worker` is released once every required check passes) and on the label `needs-decision` that `plan-issue` sets and removes; for `pending-check` it reads the required checks like `run-context.py` (`repos/<o>/<r>/rules/branches/<default>`, `repos/<o>/<r>/branches/<default>`) and `gh pr checks --required --json name,bucket`; it runs `issue-context.py` by the relative path `../../work-issue/scripts/`. For `--owner <login>` it reads `users/<owner>` and `search/issues` with `user:<login>`, as `run-context.py` does; both depend on the search result fields `items`, `total_count`, `incomplete_results`, `repository_url`, `number`, `labels` (`has-work.py`) and on `user:` matching organisations too. `dispatch.py` depends on the `WORK`/`ERROR`/`NONE` lines and exit codes of `has-work.py --all` (same directory), on `systemd-escape --template` for the instance name and on `systemctl --user list-units` (first column, the unit name) and `systemctl --user start --no-block`; the template units in `scheduling.md` rely on `%I` giving the repository back.
- `orchestrate-issue` (`run-context.py`) depends on `$CODING_ROOT` (same scan as `classify.sh --all`), `gh repo clone`, the line kinds of `issue-context.py` and `run-context.py`, the GraphQL query `issue.userContentEdits` with `createdAt` and `includesCreatedEdit` (the edit check: any edit by a non-writer, whenever made, makes the issue untrusted; the revision that records the creation is not an edit) and the endpoints `users/<owner>`, `search/issues` (for `--owner`), `repos/<o>/<r>/rules/branches/<default>`, `repos/<o>/<r>/branches/<default>` (classic protection), `repos/<o>/<r>/issues/<n>/events` and `repos/<o>/<r>/collaborators/<login>/permission`.
- `inbox` (`collect.py`) reads every non-archived, non-fork repository of the owner through `gh` (`--repo` / `--here`: one repository, live, no cache and no lock; `--here` resolves it with `gh repo view` in the current directory and exits 2 when there is none, which the skill takes as the cue for the account-wide list; the header's `scope=` key says which was read), keeps one cache per owner plus `default-owner`, `refresh.lock` and `refresh.error` in `$XDG_CACHE_HOME/claude-inbox/` and reads ignore rules from `$XDG_CONFIG_HOME/inbox-ignore`. The `RUN` rows come from one `gh api repos/<o>/<r>/actions/runs?branch=<default>&per_page=100` call per repository (fields `status`, `conclusion`, `event`, `path`, `name`, `display_title`, `head_sha`, `created_at`, `html_url`, `head_repository.full_name`; the head commit's `oid` comes from the GraphQL query), and Dependabot update jobs are told apart by the shapes of `display_title` (`<ecosystem> in <dir> - Update #<id>`, `<ecosystem> in <dir> for <deps> - Update #<id>`, `Graph Update: <ecosystem> in <dir> #<id>`, and the same cut off after the dependency list): a title of none of these shapes is keyed by its workflow path, and a change of GitHub's title text splits or merges rows, and a change of a repository's Dependabot directory list splits rows the same way and leaves the old title's last red run as a `RUN` row. Its SessionStart hook only ever reads the default owner's cache and starts a detached `--background` refresh when it is stale, so a session start never waits for GitHub; the lock keeps refreshes from overlapping, and a failed background refresh is shown by the next summary; the hook prints JSON, and its line format is not parsed anywhere. Step 4 hands a picked `ISSUE` item to `work-issue:work-issue` when the session lists that skill and falls back to working it by hand otherwise, so the coupling is optional.
- `check-install-config.py` exists in `nx-migrate` (steps 1 and 2) and in `work-issue` (step 5) as byte-identical copies, because a skill calls only scripts of its own plugin and each skill works without the other plugin. A change to the script, its line kinds or its list goes into both copies in the same PR, bumps both plugins, and updates both `SKILL.md` files where they rely on the output; the `cmp` line under Commands in `docs/commands.md` checks it.
- `merge-facts.py` exists in `work-issue` and in `nx-migrate` as byte-identical copies, for the same reason as `check-install-config.py`. Each copy is called by its plugin's agent (`worker-merging.md` of `work-issue` and `nx-migrator.md` under Merging), and both agents rely on its line kinds (`VERDICT`, `HEAD`, `BASE`, `LASTBASE`, `SKIPPED`). A change goes into both copies and both agents in the same PR and bumps both plugins; the `cmp` line under Commands in `docs/commands.md` checks the copies. The script also depends on the verdict heading `## Independent local review` and the `Reviewed head:` line of `plugins/pr-review/agents/pr-reviewer.md`: a renamed heading leaves it with `SKIPPED verdict` and no merge. The `BASE` lines come from the PR timeline through `gh api graphql` (`timelineItems` with `itemTypes: [BASE_REF_CHANGED_EVENT]`, fields `createdAt`, `previousRefName`, `currentRefName`; completeness is checked against `filteredCount`, not `totalCount`, which counts events of every type): the verdict binds only the head, so a retarget after the review is otherwise invisible. `LASTBASE` is the newest base change regardless of the verdict, because after the round a `BASE` line causes, the verdict is newer than the change and no `BASE` line is printed any more; the agents compare it with the start time of the required checks only (names from `gh pr checks --required`, start times from `statusCheckRollup`) and refuse the merge while any of them started before it (a retarget keeps the head SHA and a `pull_request` workflow without the `edited` type does not run again), `issue-worker` with a stop marker of reason `other`, `nx-migrator` with a report (#189). A `BASE` line makes the agents run one further review round on the current head (not bound by the limit of 4: only a person retargets a PR). The reviewer reads `baseRefName` at the start and again just before the verdict and repeats its base-dependent checks when it changed (`pr-reviewer.md`, "Verdict"; this paragraph depends on that rule); a retarget between the reviewer's last read of the base and the posting of the verdict is older than the verdict and caught by nothing. A resume round on a head without verdict is not bound by the limit of 4 when the PR already has four or more verdicts: only somebody else's push or `issue-worker`'s own branch update (`update-branch` on a branch behind its base) creates such a head. No merge condition depends on what an account posts after the verdict: the agents handle automated reviewers nowhere (#225).
- `repo-commands.py` (work-issue only, not shared with `nx-migrate`) composes the commands of a caller of `build-test-publish.yml` exactly as `test-and-build.yml` of `tehw0lf/workflows` runs them (`<tool> <input>` for install, format, lint, test, e2e and build_branch; `npm` always `npm ci`, `yarn` always `yarn install --frozen-lockfile`; `cargo` additionally `cargo fmt --all -- --check` and `cargo clippy --all-targets ...`; no commands for `tool` absent or `none`). A change in how that workflow composes or defaults these steps is mirrored in the script's docstring and code in the same PR. `work-issue` `SKILL.md` steps 4 to 7 rely on its line kinds (`CALLER`, `CI`, `TOOLCHAIN`, `SCRIPT`, `MAKE`, `PROJECT`, `DOC`, `WORKFLOW`, `FALLBACK`, `SKIPPED`). A new fallback row goes into the docstring and the code (not into `SKILL.md`), only after its commands were run against the real tool; the rows for bun, Maven, Composer and Gradle without a wrapper are missing for that reason.
- `scripts/review-rounds.py` depends on the verdict layout of `plugins/pr-review/verdict-layout.md` (the agent reads it before it writes the verdict) and on the fixed lines that `plugins/pr-review/agents/pr-reviewer.md` repeats, which also give the flat fallback used when the file cannot be read: the first line `## Independent local review` (a comment with any other first line is not counted, so a renamed heading turns every new verdict into a `NOVERDICT` line without a warning), the count line `**Blocking: <n> · Fix in PR: <n> · Follow-up: <n>**` and, for verdicts without the count line (the flat layout before #31), the `### Blocking`, `### Fix in PR` and `### Follow-up` headings. The origin line below the heading is not read and must not displace the heading from line 1. Change the layout and the script together.
- `verify-nx-provenance.js` pins the expected publisher (`nrwl/nx`, `.github/workflows/publish.yml`, tag ref) — an upstream release-process change shows up there as a failed check.
